# 类型对齐与分桶覆盖（P0-1，2026-11-16）

## 一、关键结论：覆盖率要看"桶"，不能看总数
| 桶 | 总数 | 有签名 | 覆盖率 |
|---|---|---|---|
| 全部符号 | 74,785 | 56,538 | **75.6%** |
| **public（无下划线前缀）** | 20,954 | 12,163 | **58.0%** |
| private（`_x`） | 52,022 | 43,062+ | 82.8%（此前统计） |
| dunder（`__x`） | 1,809 | 1,313 | 72.6% |
| **documented（.fnd 有文档）** | 7,586 | 7,514 | **99.1%** |

**要点**：此前挖到的 31,352 条签名里，**只有 11 个**是 `.fnd` 文档函数 —— 挖掘主要在补**未文档化的内部函数**。
真正影响可用性的是 **public 桶（58.0%）** 和 **documented 桶（99.1%）**。

## 二、本轮实际改动
1. **零参函数补全**：从 `.fnd` 的 `fname()` 形式识别 **657 个零参函数** → documented 从 90.4% → **99.1%**；
2. **注册表分桶统计**：`ApiRegistry.coverage()` 新增 `public / public_with_signature / public_coverage`；
3. **public 桶挖掘启动**：9,300 个 public 缺签名函数，已完成第 1 块（**509 个**，命中率 50.9%，
   低于 private 的 78% —— public 里很多是类构造/无 arglist 的函数）；
4. **实调用率基线**：抽样 40 个有签名只读函数真机调用 → **39/40 = 97.5% 成功**
   （唯一失败是业务错误 `EXPORTDIE-30112`，非接口问题）。

## 三、下一步（按数据修正计划）
- 继续 public 桶剩余 8,791 个（9 块，约 40–70 分钟）；

- 之后再谈 `.fnd` 类型与 arglist 的类型对齐（`arglist` 里仅 1,088 条带类型字母，天花板有限）。
