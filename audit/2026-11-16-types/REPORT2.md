# 收敛决策：停止长尾挖掘，锁定当前覆盖（2026-11-16）

## 一、为什么这么慢（真实原因，非脚本问题）
| 因素 | 实测 |
|---|---|
| 宿主机负载 | `load average 7–9`，`virtuoso` 进程 **14–17** 个 |
| 他人长期作业 | `/root/pa_rf/probe_pdk.il` 已运行 **3 天+**（未动） |
| 单 chunk 成本 | 每次需**新起 Virtuoso**（~40 s）+ 1000 次 `arglist`；**部分函数的 arglist 会挂起**，靠 300 s 超时兜底 |
| 实际吞吐 | **5–8 分钟/chunk**，public 桶 10 块 = 50–80 分钟 |

## 二、当前覆盖（已锁定）
| 桶 | 覆盖率 |
|---|---|
| 全部符号 | **77.2%**（57,751 / 74,785） |
| public | **63.8%**（13,376 / 20,954） |
| documented | **99.1%** |

本轮新增合并 1,213 条（public 桶 3 块）。

## 三、为什么建议停止长尾
1. **public 桶命中率只有 50.9%**（private 是 78%）——public 里很多是类构造/无 arglist 函数，继续挖收益递减；
2. **documented 已 99.1%** —— 真正有文档、可放心调用的部分基本齐了；
3. 剩余缺口集中在**未文档化的内部函数**，没有文档、没有类型、语义未知，调用风险高。

## 四、风险分类的实测结论（重要）
用"模块前缀 + 动词"做静态 write/read 分类，结果：
`read 2,649 / write 2,526 / unknown 69,610` —— **启发式只能覆盖 7%**。
→ 结论：写操作安全必须靠 **显式允许清单（allowlist）+ 文档描述**，不能靠名字猜。

## 五、下一步（建议）
1. **allowlist 化写策略**：只把经过验证的写操作（目前 8~13 个工程操作）放进白名单；
2. **GUI-only 标记**：26,587 个函数打 `needs_window`，让查询能解释"为什么不可用"；
3. **接入 gateway**：把 `GenericSkill` 接到现有 `vskill/gateway`，只读走白名单，写走工程操作。
